# Current state

Implemented and verified on `main`:

- **BoZ USD/ZMW**: live quote, conflict-aware persistence, stored history, manual historical backfill from the official JSON source, provenance, dashboard/detail UI, chart and `FX USDZMW` / `USDZMW` commands.
- **Treasury Bills**: live BoZ auction adapter for 91D/182D/273D/364D, persistence, manual historical backfill, stored history API/charts, dashboard/detail UI and tenor commands.
- **Government Bonds**: live BoZ auction adapter for 2Y/3Y/5Y/7Y/10Y/15Y, persistence, manual historical backfill, stored history API/charts, dashboard/detail UI and tenor commands.
- **ERB fuel**: long-run XLSX retail/wholesale history, current retail prices from supported monthly press statements, strict OCR fallback for image-only press statements, pump/wholesale build-up ingestion, stored APIs, charts/detail views and `FUEL` commands.
- **Ministry agriculture**: maize and soya national-average monthly prices from the verified Layout B bulletin family, stored history, API/UI/chart and `AGRI` / `MAIZE` / `SOYA` commands.
- **Global oil (Brent, WTI)**: monthly World Bank Pink Sheet averages in USD/bbl (stored history, stored-only API, UI chart and `OIL` / `OIL BRENT` / `OIL WTI` commands, manual `backfill_oil` import); see "Global oil benchmarks (monthly)" below.
- **OIL ZM (derived)**: monthly Brent in ZMW per barrel derived on request from stored World Bank Brent and stored BoZ USD/ZMW (nothing derived is persisted); see "OIL ZM (derived monthly)" below.
- **Bitcoin (local/internal)**: Bitstamp BTC/USD live and stored daily OHLCV plus an indicative derived BTC/ZMW (`BTC` / `BTC USD` / `BTC ZMW`); public rights remain `review_required`; see "Bitcoin" below.
- **Sovereign yield curve (derived)**: the published auction-yield tenor curve built from stored BoZ T-bill and Government-bond auctions (`CURVE ZM`); see "Sovereign auction yield curve (derived)" below.
- **Provider/source discipline**: exact Decimal storage, source provenance, fail-closed parsing, idempotent inserts, conflict detection without overwrite, no fabricated values and no raw-source storage unless explicitly justified.
- **CI**: API tests run with PostgreSQL integration coverage and the web build runs on GitHub Actions.

Not implemented: LuSE market data (blocked pending suitable access), FRA procurement prices, ZAMACE spot prices, copper, gold (source discovery done: World Bank preferred, licence confirmation pending; see `docs/research/gold-provider-discovery.md`), macro indicators, general yield-curve analytics (only the four fixed published-tenor spreads below exist), watchlist persistence, authentication, alerts, scheduled ingestion, frontend test runner/lint step, cross-market compare/correlation tools, Atlas and the long-term expansion domains in `docs/ROADMAP.md`.

Important source limitations:
- BoZ USD/ZMW JSON history begins on 2026-01-22; the older analyst XLSX was deliberately not imported.
- LuSE remains blocked pending an acceptable machine-readable source or authorised access.
- ZAMACE spot integration is blocked pending permission / suitable reuse rights.
- Ministry agriculture source discovery and the first maize/soya national-average implementation are complete; older Layout A bulletins remain deferred because of their printed `ZMK` labels.
- Migrations remain plain SQL in `db/init` and must be applied manually to existing database volumes.

Known limitations:

- History is limited to what the JSON view serves (from 2026-01-22) plus quotes retrieved by this app. The filter's timezone is undocumented (harmless for whole-day windows given the 07:30-13:30 UTC slots).
- A few published rows are inconsistent and stored as published, e.g. buy > sell on 2026-03-19 07:30Z and 10:30Z; the live adapter and backfill share one source-selection policy (UTC hours 07/10/13, mirroring the BoZ site's latest-rate selection; its series chart is unfiltered, and unlike the site there is no fallback), so rows in those slots are trusted as published.
- A conflicting stored row is detected (safe warning) but not resolved: the live quote is returned unsaved and the stored row is kept; there is no reconciliation tool.
- T-bills: BoZ published tender 23/2026 (2026-11-12) with a duplicated 273-day record (the 182-day values filed under 273). It is rejected whole and reported in `skipped_tenders`; rows fall back to tender 22/2026.
- Redistribution and commercial-use terms of BoZ data are unreviewed.
- Migrations are plain SQL in `db/init` (applied automatically only on a fresh database volume).

## Treasury Bills
- Source: official BoZ Drupal JSON:API `/jsonapi/node/tbills_auction_results` (what the BoZ Treasury Bills page itself reads; public, no auth). One node per tender (`title` "22/2026", `field_tbills_auction_date`) with one included paragraph per tenor (91/182/273/364 days): ISIN, yield, discount. Field names differ per tenor and are matched strictly. Amounts, cut-off and yield ranges exist only in linked PDFs and are **not** modelled (no PDF parsing).
- `GET /api/v1/treasury-bills/latest` (newest row per tenor, each with its own auction date; `missing_tenors`, `skipped_tenders`) and `GET /api/v1/treasury-bills/{91D|182D|273D|364D}` (422 invalid tenor, 404 none recent, 504 timeout, 502 other). Fetches the 5 most recent tenders per request; a tender failing validation (bad number/date/ISIN/rate, duplicate tenor) is rejected whole, never repaired. `stale` = auction older than 21 days (heuristic).
- Persistence: `treasury_bill_auctions` (`db/init/003_treasury_bill_auctions.sql`, apply manually to existing volumes), unique on `(auction_date, tender_number, tenor_days)`; same conflict-aware rules as `fx_rates` (identical = no-op, different = rollback, never overwritten). Best-effort: the live response is returned if saving fails.
- Commands: `TBILL ZM`, `TBILL 91D|182D|273D|364D`. Stored historical observations are exposed by `/treasury-bills/history` and charted in the detail view; the historical import is documented in the Fixed-income history section below.

## Government Bonds
- Source: official BoZ Drupal JSON:API `/jsonapi/node/bond_auction` (what the Government Bonds page reads; public, no auth). One node per auction (title `07/2026/BA`); `field_bond_auction_date` is an ISO datetime with explicit +02:00 offset, its calendar date being the auction date (every 2026 value is a Friday); one included `paragraph--<N>_year(s)_bond` per tenor (2/3/5/7/10/15) with ISIN, coupon, yield. Field names differ per tenor and are matched strictly; the tenor label must agree with the record type. Nodes before 12/2025 are empty placeholders (rejected as "no published tenors"). Amounts, cut-off coupon/yield and ranges exist only in PDFs and are **not** modelled.
- Reopenings: 7Y/10Y/15Y repeat the same ISIN and coupon across auctions with new yields; 2Y/3Y (and 5Y) are new ISINs. Identity is `auction_date + tender_number + tenor_years`, never the ISIN.
- `GET /api/v1/government-bonds/latest` and `/{2Y|3Y|5Y|7Y|10Y|15Y}`: newest row per tenor among auctions that contain it; `missing_tenors`; `skipped_tenders` (informational); per-row `newer_rejected_tenders` (rejected auctions dated after the row; non-empty = fallback; same semantics as T-bills). Discovery walks the BoZ archive newest-first, 50 auctions per page via the API's own `links.next` (same endpoint only), sequentially, stopping once all six tenors have a valid row or the archive ends (currently 3 requests: the archive is 110 tenders, 8 with data); a 10-page cap that is reached with tenors unfound and a `next` link still present fails closed (502). So `missing_tenors` means "not in the whole archive". A tenor can therefore come from an old auction (5Y: 02/2026); no stale flag. Duplicate auctions across pages collapse if identical and fail if conflicting. 422 invalid tenor, 404 none recent, 504 timeout, 502 other.
- **No `stale` flag** by design: the issuance calendar is a quarterly PDF (not machine-readable) and observed gaps between 2026 auctions were 21 to 63 days, so no defensible threshold exists. Each row shows its own auction date.
- Persistence: `government_bond_auctions` (`db/init/004_government_bond_auctions.sql`; apply to an existing volume with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/004_government_bond_auctions.sql`), unique on auction identity; same conflict-aware rules as T-bills; best-effort save.
- Live finding (2026-11-12): tender `03/2026/BA` has a malformed 15Y ISIN (`ZM100007709`, 11 characters). It is rejected whole and reported neutrally (older than every displayed row, so no fallback claim).
- Commands: `BOND ZM`, `BOND 2Y|3Y|5Y|7Y|10Y|15Y`; dashboard card `10Y GRZ BOND`. Stored historical observations are exposed by `/government-bonds/history` and charted in the detail view. The sovereign yield curve remains planned.
- **Validation granularity:** tender-level failures reject the whole tender (bad tender number or date, malformed/duplicate references, a referenced record missing, two records for one tenor); tenor-level failures (invalid ISIN/coupon/yield, label mismatch, unpublished record, unknown record type) reject only that record and valid siblings stay usable. Nothing is repaired or trimmed. Rejections are kept as `{tender_number, auction_date, affected_tenors, scope}` (no error text). A valid tender with zero result records is "no results", not a rejection. Valid tenors this adapter does not model (e.g. a 20-year record) are ignored.
- **Fallback rule:** a row is a fallback only if a rejected record dated strictly after it could have carried that same tenor (its own tenor, or a tender-level rejection). `unverified_tenors` lists missing tenors a rejected record could have carried.
- **Live (2026-11-12):** BoZ's archive has 110 tenders, 8 with data; each of 12/2025, 01/2026, 02/2026 and 03/2026 had one malformed ISIN in a different tenor (15Y, 7Y, 3Y, 2Y). Their other tenors are now accepted, so 5Y resolves to 02/2026/BA (2026-02-13), and all six tenors are found in a single 50-auction page.

## Fixed-income history
- Manual jobs (no scheduler): `python -m app.jobs.backfill_tbills --from YYYY-MM-DD [--to YYYY-MM-DD] [--dry-run]` and `python -m app.jobs.backfill_bonds ...`. Both use the live adapters' parsers (T-bills: whole-tender rejection; bonds: tender-level vs tenor-level rejection), the collections' standard date filter (`field_tbills_auction_date`, `field_bond_auction_date` with +02:00 bounds), 50 per page, `links.next` (same endpoint only), sequential, 1 s apart, no retries, at most 10 pages (a truncated search fails). Future dates and `--from > --to` are rejected; every page is validated before one atomic write through the existing conflict-aware stores; `--dry-run` never touches PostgreSQL. Output is counts only. Empty "no results" tenders are counted separately, not as rejected.
- History APIs read stored rows only (never BoZ): `GET /api/v1/treasury-bills/history?tenor=91D|182D|273D|364D&range=1M|3M|6M|1Y|ALL` (default 364D, 1Y) and `GET /api/v1/government-bonds/history?tenor=2Y..15Y&range=3M|6M|1Y|ALL` (default 10Y, 1Y). Ascending by auction date, decimal strings, one point per real auction (a reopened ISIN gives one point per auction), no interpolation or forward-fill. 422 for invalid tenor/range, safe 503 if the database fails. `range` is relative to today (Africa/Lusaka).
- Migration `db/init/005_fixed_income_history_indexes.sql` adds `(tenor, auction_date)` indexes only (apply to existing volumes with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/005_fixed_income_history_indexes.sql`). Note: `003`/`004` must be applied too; the local dev DB lacked `treasury_bill_auctions` until this task (live T-bill saves had been silently best-effort failing).
- UI: each T-bill/bond detail view has a tenor + range selector and a Lightweight Charts yield line with one marker per auction; empty, single-point, loading and database-unavailable states.
- Real import (2026-11-12, dev DB): T-bills archive 336 tenders (2014-01-09..2026-11-12, only 21 with data, 315 empty), 52 valid rows from 13 tenders (2026-02-05..2026-10-29), 8 rejected tenders (23/2026 duplicate 273D; 14, 13, 12, 10, 08, 07/2026 have trailing whitespace in the tender number; 04/2026 has a 182D ISIN with trailing whitespace), 52 inserted, re-run 52 already present. Bonds: 110 auctions (102 empty), 39 valid rows (2025-12-19..2026-09-25), 1 tender-level and 4 tenor-level rejections, 39 inserted earlier via live reads, re-run 39 already present.
- Source-quality caveat: the T-bill parser deliberately does not trim whitespace, so six 2026 tenders whose only defect is a padded tender number are excluded from T-bill history. Deciding whether to accept them is a policy choice.

## ERB Zambia fuel
- Source: ERB's public WordPress media API (`/wp-json/wp/v2/media?search=PUMP AND WHOLESALE PRICES&mime_type=application/zip`) locates the official archive ZIP (`.../uploads/files/PUMP-AND-WHOLESALE-PRICES-2012-2026.zip`, about 30 KB, one XLSX). Sheets `Wholesale Prices` and `Retail Prices ` (note the trailing space; matched after stripping). Monthly rows (`Year`, `Month`, then Petrol, Diesel, Kerosene, Jet A-1, Low Sulphur Gas oil in K/L); the wholesale sheet also has HFO/LPG/Bitumen (`Kg/L`, ambiguous unit, ignored). Retail covers 2012-01..2026-10 (the archive was published 2026-10-08, so the November press-release prices are **not** in it; they exist only as PDFs, which are not parsed). Month granularity: `effective_date` is the first day of the pricing month.
- **Precision rule:** ERB archive prices are normalized to the official workbook's displayed two-decimal ZMW precision. Binary Excel floating-point representation is not treated as additional published precision. Cells formatted `0.00`/`#,##0.00` become `Decimal(f"{v:.2f}")` and must equal the stored value within 1e-9; a cell whose stored value carries precision the format hides (135 wholesale cells, e.g. 20.00448 shown as 20.00) is rejected and counted, never rounded. `General` cells display up to 15 significant digits and are normalized through that. Any other format, header, sheet or value type fails the parse. `-`, blank and missing cells are "not published" (NULL), never 0.
- **Duplicate months:** the workbook lists some months twice (mid-month changes, no day given). All non-missing observations of a month/product are recorded before any is rejected. Identical usable duplicates collapse; if usable duplicates differ, or any duplicate is rejected (hidden precision, junk/non-finite/non-positive value), the whole product-month is ambiguous and omitted (`ambiguous_duplicate_cells`), never resolved by row order. A `-`/blank cell next to a valid value is not a competing observation and the valid value is kept. A single rejected observation is counted (`hidden_precision_cells` / `invalid_value_cells`) but is not "ambiguous". Result is independent of worksheet row order.
- **Wholesale precision:** retail/public pump prices use the official displayed 2dp precision; some wholesale cells carry higher precision and are preserved only where the workbook presents it (`General` format), never rounded away behind a `0.00` format (those are rejected). Float noise within 1e-9 in a `0.00` cell still normalizes to the displayed 2dp value.
- Table `zambia_fuel_prices` (`db/init/006_zambia_fuel_prices.sql`; apply to an existing volume with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/006_zambia_fuel_prices.sql`), unique on `(effective_date, product, price_type, unit)`, same conflict-aware rules (identical numeric = no-op, different = conflict, atomic rollback). Products `PETROL, DIESEL, KEROSENE, JET_A1, LSGO`; `price_type` retail/wholesale; unit litre.
- Job: `python -m app.jobs.backfill_fuel --from YYYY-MM-DD [--to YYYY-MM-DD] [--dry-run]` (manual; archive downloaded into memory only; counts only; future dates and `--from > --to` rejected; dry-run never touches PostgreSQL). It needs `openpyxl` (in `requirements.txt`; rebuild the API image to run it in-container; the API runtime itself does not import it).
- API (stored data only, ERB is never called): `GET /api/v1/fuel/latest` (newest retail per product + `missing_products`), `GET /api/v1/fuel/{PETROL|DIESEL|KEROSENE|JET_A1|LSGO}` (422 invalid, 404 none), `GET /api/v1/fuel/history?product=&range=1Y|3Y|5Y|ALL&type=retail|wholesale` (ascending, no interpolation, 503 on database failure).
- UI: `PETROL ZM` card; `FUEL ZM|PETROL|DIESEL|KEROSENE|JET|LSGO` opens the fuel view (latest table, per-product monthly retail chart with range selector). A neutral note appears when the newest stored month is before the current month.
- Real import (2026-11-12, dev DB): 370 workbook records examined, 1389 valid rows (retail: PETROL/DIESEL/KEROSENE 173 each, LSGO 141, JET_A1 49; wholesale: PETROL 143, DIESEL 143, KEROSENE 146, JET_A1 145, LSGO 103), 211 not-published cells, 135 hidden-precision wholesale cells rejected, 52 ambiguous duplicate cells omitted; 1389 inserted, re-run 1389 already present, 0 conflicts.
- The XLSX archive remains the long-run history source. Monthly PDF build-ups and supported press-statement retail prices are implemented in the section below; Jet A-1 posted airfield prices outside the supported statements remain unmodelled.

## ERB latest month + build-ups
- **Discovery:** ERB's media API (`/wp-json/wp/v2/media?search=pump&mime_type=application/pdf`, up to 5 pages) lists the monthly PDFs; each is classified by filename (never a hard-coded month) into `press` (`/PressStatements/CurrentFuelPumpPrices<Month><Year>.pdf`), `pump` (`...PUMP-PRICE-BUILD-UP`), `wholesale` (petrol/diesel/kerosene) and `jet` (Jet A-1) under `/files/FuelPumpPrices/`. Only `https://www.erb.org.zm` PDFs are fetched (content type and size checked). Two different files for one month/kind are ambiguous and excluded. Files without a month in the name (e.g. `CurrentFuelPumpPrices-1-1-1.pdf`) are ignored. ERB's media listing has no documents for August 2026.
- **Parsing:** text-layer build-up PDFs use `pdfplumber` with strict source-specific validation. Product heading, units, month and component rows must be complete; malformed component rows reject the whole document instead of being treated as notes. Only recognised continuation-note structures beside their known rows are accepted. `-` = NULL (stored as NULL, never 0), `(2,117.40)` = negative, and numeric text is parsed directly to Decimal. Unknown or duplicated rows fail the document. Two rows both labelled `TOTAL (Excl VAT)` get distinct codes by position (`TOTAL_EXCL_VAT_BEFORE_OMC_MARGIN` / `..._AFTER_OMC_MARGIN`). Renamed rows map to one code only where verified equivalent; the printed label is always kept. US$-priced wholesale rows are separate codes from K/M3 rows.
- **Supported layouts (verified, September 2025 to November 2026):** pump build-ups 14/14 months; petrol/diesel/kerosene wholesale 13/14 (not December 2025); Jet A-1 12/14 (not February/March 2026); text press statements for December 2025, January, February, March, May, July and October 2026. Not supported (counted as `unsupported_documents`, no one-off parsers): press statements for September-November 2025 (different effective-date wording), the odd wholesale/Jet layouts above, and everything before September 2025. XLSX remains the long-run price history.
- **Scanned press statements (OCR fallback):** a press statement with **no text layer at all** is read with Tesseract (`app/services/erb_ocr.py`), only from the manual job and never from an API request. A text PDF that fails validation is *not* OCR'd. The page is rendered in memory at 300 DPI and read by two deterministic passes (`--psm 6` and `--psm 4`); each pass must satisfy the same strict press grammar (title month, "at midnight on" wording equal to the day before the pricing month, labelled PETROL/DIESEL/KEROSENE/JET A-1 rows, strict `NN.NN` positive prices, no repair of misread digits) and both must agree on month and every price. PETROL/DIESEL/KEROSENE must also equal the month's official pump build-up uniform price (ZMW/m3 ÷ 1000, rounded half-up to 2 decimals); without that build-up the scanned statement is rejected. Jet A-1 has no such check and is accepted only through the same strict two-pass grammar. Images, OCR text and PDFs are never stored or returned. The extraction method is operational: the job reports `text_press_parsed` / `ocr_parsed` / `ocr_rejected` counts; the stored rows are identical either way (`provider = erb`).
- **Effective date:** a press statement says the prices take effect "at midnight on 30th September 2026" for the October 2026 prices. Retail rows keep the archive's identity, the first day of the pricing month (2026-10-01), so XLSX and PDF rows for a month collide and are compared: identical = no conflict, different = conflict (nothing written). The statement's midnight date must be the day before the pricing month or the document is rejected. Build-up rows use the same `effective_date` convention. In short: `effective_date` in `zambia_fuel_prices` identifies the ERB pricing month, matching the XLSX archive's monthly identity; the statement's literal midnight date is validated, not stored.
- **Reconciliation (checks only):** PETROL/DIESEL/KEROSENE press prices must equal the build-up uniform pump price converted from ZMW/m3 to ZMW/litre and rounded half-up to the published two decimals. The build-up is never used as the source of the retail price. Jet A-1 has no pump build-up reconciliation and therefore relies on the strict statement parser/OCR agreement rules. Text and scanned statements that fail validation are rejected rather than repaired.
- **Schema:** `zambia_fuel_build_up_items` (`db/init/007_zambia_fuel_build_up_items.sql`; apply with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/007_zambia_fuel_build_up_items.sql`): one row per product + component with `component_code`, source `component_label`, `position` (ERB order), nullable `amount`, `currency`, published `unit` ('' when none printed), `note` (printed rates/prose such as wharfage text), unique on `(effective_date, build_up_type, product, component_code, unit)`; Jet A-1 is `build_up_type = wholesale`, `product = JET_A1`. Same conflict-aware rules (NULL equals NULL; a NULL vs a published value is a conflict; one transaction for retail prices and build-ups).
- **Job:** `python -m app.jobs.backfill_oil --from YYYY-MM [--to YYYY-MM] [--dry-run]`. One page request, one workbook download (official HTTPS hosts only; redirects are validated hop by hop, at most 3; Content-Type, 15 MB cap and OOXML checks), strict parse, one atomic transaction, counts-only output, nothing stored on disk. Requested months must lie within the workbook; a `--from` after the newest month is an error (also without `--to`), never clamped. `--dry-run` validates discovery, structure, parsing and range selection but does not touch PostgreSQL, so it cannot detect conflicts with stored values. Run it monthly by hand after the World Bank update (there is no scheduler). **On a conflict** the whole import stops, names up to 5 benchmark/month identities (never prices) and writes nothing; narrow `--from` past the conflicting month to keep importing newer months. Revision modelling is deferred.
- **API / UI:** `GET /api/v1/fuel/build-up?product=&type=pump|wholesale&month=YYYY-MM` (stored only; month optional = newest; 422 invalid, 404 none, 503 database). The fuel detail view has `RETAIL HISTORY | PUMP BUILD-UP | WHOLESALE BUILD-UP` for the selected product; rows are shown in ERB's order with the published unit, without claiming they add up.
- **Real verification (2026-11-13, dev DB), 2025-09..2026-11:** 15 months and 56 discovered documents; 4 press statements are scanned. November 2026 OCR succeeds with PETROL 33.06, DIESEL 34.45, KEROSENE 32.08 and JET_A1 34.51. April, June and September scanned statements remain deliberately unsupported because they fail the narrow validation rules. After the stricter wholesale-row fix, January/February 2026 wholesale documents with incomplete BPS Premium rows are also unsupported. The idempotent re-run inserted nothing: 32 retail rows and 1719 build-up rows were already present.


## Ministry agriculture national averages
- **Source:** official Ministry of Agriculture / Department of Agribusiness and Marketing monthly market-information bulletin PDFs discovered through the Ministry WordPress media API. The first supported family is Layout B; the verified bulletin covers April 2025 through January 2026.
- **Semantics:** only grain rows `MAIZE` and `SOYA_BEANS`; `market_type = national_average`, `price_basis = indicative_average`, national scope, source unit ZMW/kg. Seed, meal, flour, fertilizer and other rows are not imported.
- **Parser:** text-layer PDFs only. Table 3 must contain ten calendar months and exactly the expected row shape; only the ten published prices are ingested. Printed percentage-change values are ignored. Table 1 must exactly reconcile the December and January maize/soya prices or the document is rejected. Known older Layout A bulletins with `ZMK/MT` / `ZMK/Kg` are deliberately unsupported rather than silently re-labelled.
- **Dates:** each observation is a calendar month with `period_start` / `period_end`; upload/publication date is stored separately and is never used as the observation date.
- **Schema:** `db/init/008_zambia_agricultural_prices.sql`. National-average identity uses a partial PostgreSQL `UNIQUE ... NULLS NOT DISTINCT` index across provider, commodity, reporting period and nullable dimensions. Same identity + same numeric value is idempotent; a different value is a conflict and is never overwritten.
- **Job:** `python -m app.jobs.backfill_agriculture --from 2025-04 [--to 2026-01] [--dry-run]`. The job discovers official PDFs, accepts Layout B only, validates all observations before one atomic write, logs counts only, and stores no raw PDF/text.
- **TLS:** certificate verification is always enabled. If the Ministry server's incomplete certificate chain is not resolved by the host trust store, set `MOA_CA_BUNDLE` to a trusted CA bundle containing the required intermediate; the importer never uses `verify=False`.
- **API:** stored data only: `GET /api/v1/agriculture/latest`, `GET /api/v1/agriculture/{MAIZE|SOYA_BEANS}`, and `GET /api/v1/agriculture/history?commodity=&range=1Y|3Y|ALL`.
- **UI:** one `MAIZE ZM` dashboard card plus an agriculture detail view with maize/soya monthly history. The period is displayed prominently and described as an indicative national average, not a live trade price. Commands: `AGRI ZM`, `MAIZE ZM`, `SOYA ZM`, `MAIZE AVG`, `SOYA AVG`.
- **Deferred:** FRA is a separate procurement/policy branch; ZAMACE remains blocked pending permission / suitable reuse rights. Neither is folded into the Ministry series.

## Global oil benchmarks (monthly)
- **Source:** World Bank Commodity Price Data (The Pink Sheet), monthly workbook `CMO-Historical-Data-Monthly.xlsx`, found through the official Commodity Markets page (`https://www.worldbank.org/en/research/commodity-markets`; the file's URL hash changes every release, so the page is the discovery mechanism and must contain exactly one link). No API key. Direct source adapter (`app/services/worldbank_oil.py`) behind FastAPI; it deliberately does not go through OpenBB. See `docs/research/global-oil-sources.md`.
- **Pivot:** FRED/EIA daily spot (via OpenBB) was built first and evaluated, then set aside. During source evaluation, the applicable FRED API terms and EIA source notes did not provide a sufficiently clear fit for ZM Terminal's persisted-history design, so the implementation uses the World Bank Pink Sheet instead. This is a fit-for-use decision, not criticism of those providers; OpenBB and its FRED provider remain installed for other uses.
- **Mapping:** sheet `Monthly Prices`; commodities are columns and months are rows. Columns are located by exact header label `Crude oil, Brent` and `Crude oil, WTI` (never by position), unit row `($/bbl)`, month key `YYYYMmm` in column A (`2026M10`), consecutive from `1960M01`. Title, subtitle, a single `Updated on <date>` line, unit labels, month keys and gaps are all checked; any change fails closed. Only the missing marker `…` (WTI before 1982) means "not published"; a blank Brent/WTI cell is a malformed workbook, and nothing is ever zero. The workbook holds monthly averages; the PDF edition labels them "Monthly Averages". Cells display one decimal; values are read through `.15g` and any value with more than two decimals is rejected.
- **Semantics:** one row per calendar month (`period_start` first day, `period_end` last day), USD per barrel, `price_basis = monthly_average`. Not daily, not live, no invented observation day. Brent = Crude oil, U.K. Brent 38° API; WTI = Crude oil, U.S. West Texas Intermediate 40° API (the workbook's own descriptions). Separate series, never combined, never converted to ZMW.
- **Cadence and revisions:** updated about the 2nd business day of the month (catalog metadata). The workbook contains a `Mismatch Details` sheet that compares "Current" and "Uploaded" cells, and observed historical values may differ across releases; ZM Terminal therefore treats a changed stored observation as a conflict pending explicit revision modelling, and never overwrites. `publication_date` is the `Updated on` date of the release that first supplied the stored value and is checked to be on or after the end of the newest month it publishes, and not in the future relative to retrieval.
- **Licence (open before any public or commercial deployment):** the World Bank Data Catalog entry "Commodity Prices - History and Projections" (dataset 0038238, https://datacatalog.worldbank.org/search/dataset/0038238/commodity-prices-history-and-projections) is classified Public and lists Creative Commons Attribution 4.0 (checked 2026-11-14). The official Commodity Markets page links the monthly Pink Sheet workbook. Not yet established: that the catalog licence applies to that workbook. The catalog metadata also lists an annual periodicity, the workbook carries no licence text, and the Pink Sheet PDF footer reads "Official Use Only". The provider policy therefore marks redistribution and commercial use `review_required` (normalized storage is allowed, raw workbook storage is disabled, attribution is required and shown). Confirm applicability with data@worldbank.org before public redistribution or commercial deployment; this does not block local development or the code PR. The UI shows `World Bank Pink Sheet` with a link, and the licence note only in the detail provenance ("Catalog licence: CC BY 4.0 · workbook applicability under review").
- **Schema:** `db/init/009_global_oil_prices.sql`, one table, unique on `(provider, benchmark, period_start, period_end)` (that index also serves range reads), `CHECK` constraints for benchmark, provider, USD, barrel and exact calendar-month periods, no positivity constraint. Same identity and numerically equal value is a no-op; a different value is a conflict that rolls back the whole import and is never overwritten. Apply to an existing volume with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/009_global_oil_prices.sql`.
- **Job:** `python -m app.jobs.backfill_oil --from YYYY-MM [--to YYYY-MM] [--dry-run]`. One page request, one workbook download (official HTTPS hosts only, 15 MB cap), strict parse, one atomic transaction, counts-only output, nothing stored on disk. Requested months must lie within the workbook; run it monthly by hand after the World Bank update (there is no scheduler).
- **API (stored data only; the World Bank is never called):** `GET /api/v1/oil/latest`, `GET /api/v1/oil/{BRENT|WTI}` and `GET /api/v1/oil/history?benchmark=&range=1Y|3Y|5Y|ALL`. A database failure is a safe 503; nothing stored is a normal empty/404 response.
- **Freshness:** no live/fresh market status. The latest source month is shown with publication and retrieval dates. Month logic uses the Africa/Lusaka calendar like the other domains. `stale` means the newest stored month is more than 2 calendar months before the current month (`OIL_STALE_AFTER_MONTHS` in `app/schemas/oil.py`, returned as `stale_after_months`, displayed by the UI); this is an application heuristic.
- **UI:** a `BRENT` card ("World Bank · Oct 2026 monthly", "Monthly average, not a live quote") and a `GLOBAL OIL · MONTHLY BENCHMARKS` view with Brent and WTI, unit, month, source/period/publication/retrieval and a 1Y/3Y/5Y/ALL monthly chart (markers off above 250 points; months with no value stay missing). Values show exactly two decimals (display only). Commands: `OIL`, `OIL BRENT`, `OIL WTI`; each re-selects its benchmark even after a manual switch. `OIL ZM` is planned and not implemented.
- **Verified 2026-11-14 against the real workbook (updated 2026-11-03):** newest month 2026-10 (Brent 125, WTI 97.7). Dry run and import of 2025-01 to 2026-10: 22 months x 2 benchmarks = 44 rows inserted, 0 not published; an immediate rerun inserted 0 and found 44 already present. All 44 stored values were compared with the raw workbook cells (0 mismatches) and Aug-Oct 2026 matched the PDF edition. Only 2025-01 onward is imported so far; the workbook also holds Brent from 1960 and WTI from 1982.
- **OpenBB exposure:** `compose.yml` publishes OpenBB on `127.0.0.1:6900` only; the API reaches it over the Compose network.

## OIL ZM (derived monthly)
- **What it is:** a ZM Terminal **derived** analytical indicator, `zmw_per_bbl = brent_usd_per_bbl x usd_zmw_observed_days_avg`, per calendar month. It is not an official World Bank or BoZ series, not a Zambia retail fuel price (it is not combined with ERB fuel anywhere), not a live oil quote, not a forecast and not a daily rate.
- **Inputs (both already stored; nothing is fetched while serving it):** the World Bank Pink Sheet `BRENT` monthly average (USD/bbl, `global_oil_prices`) and the BoZ `USDZMW` `mid` observations (`fx_rates`, source `boz`, the same complete buy/mid/sell rows the USD/ZMW history shows; buy and sell are never used).
- **Observed-days FX average:** (1) assign each stored `mid` observation to its Africa/Lusaka calendar date (UTC+2, so 23:30Z on the 31st is the 1st of the next month in Lusaka, including across 31 December); (2) average that day's observations; (3) `usd_zmw_observed_days_avg` is the arithmetic mean of those daily means over the days that have stored observations. It is a mean of stored daily BoZ mid-rate averages, **not** a full-month FX average. Days are weighted equally, not by how many intraday observations they have: a day with three observations counts the same as a day with one (day 1 = 20,20,20 and day 2 = 23 gives 21.5, not 20.75). Days with no stored observation (weekends, holidays, gaps) are absent, never interpolated, forward-filled or inferred. Methodology text: "World Bank Brent monthly average × arithmetic mean of daily BoZ USD/ZMW mid averages for stored observation days (each stored day weighted equally)".
- **Arithmetic:** Decimal throughout at 40 significant digits, never float, no intermediate rounding (trailing zeros from the context are trimmed; the value is unchanged). Rounding is presentation only (the UI rounds decimal strings itself and never calculates the result). Negative Brent would multiply normally.
- **Persistence:** none, by design: both inputs are stored, the formula is deterministic, and a stored copy would add reconciliation and revision problems and hide provenance. There is no migration 010 and no derived table; a test asserts the read path writes nothing.
- **Availability:** only months with both a stored Brent average and at least one stored BoZ FX day. The BoZ machine-readable history begins on 2026-01-22, so nothing earlier is derived, and no other FX provider or the older analyst XLSX is used to extend it. Brent months without FX are omitted and counted (`brent_months_without_fx`), never filled.
- **Coverage transparency:** every month exposes `fx_day_count`, `fx_observation_count`, `fx_first_date`/`fx_last_date` (Lusaka dates used) and `fx_first_observation`/`fx_last_observation`; the UI states "Based on N stored BoZ days · M observations" directly beside the calculation. `fx_coverage` has two values. `partial_source_window` means the stored BoZ machine-readable history begins during that calendar month (January 2026: it starts on 22 Jan), so the average covers only part of it. `observed_days` means the calculation uses whatever stored days exist and asserts **no** calendar or business-day completeness; read the counts. These are different things: ordinary sparsity never receives `partial_source_window`. Sparse BoZ months remain derivable (February 2026 rests on 1 stored day with 2 observations because BoZ's own source has only those two rows for the month), and the counts show how much source data supports each value. There is no business-day or holiday calendar and no minimum-day threshold. An in-progress month would simply show its first and last observation dates.
- **API (stored data only):** `GET /api/v1/oil/zm/latest` (newest month with both inputs; 404 when there is no overlap) and `GET /api/v1/oil/zm/history?range=1Y|3Y|5Y|ALL` (slim monthly points ascending, plus the omitted count). Responses carry `classification = derived`, `derived = true`, the methodology text and id, the notice, both components and the provenance of each input (Brent: provider, release workbook URL, stable page, publication date; FX: BoZ, pair, price type, first/last observation). There is no single combined source URL. A database failure is a safe 503; there is no upstream 502/504 path. The month is chosen with the same `stale` heuristic as Brent (`stale_after_months`).
- **UI:** `OIL ZM` opens `OIL ZM · DERIVED MONTHLY BENCHMARK`: the value (for example `K2,496.78 / bbl`) with a `DERIVED` badge, the calculation line (`$125.00 Brent x 19.9742 ZMW/USD observed-days average = K2,496.78/bbl`) with "Based on 22 stored BoZ days · 66 observations" directly beneath, month, both components, a partial-source-window notice where it applies, provenance, a monthly chart with 1Y/3Y/5Y/ALL, and a per-month table of components and FX day counts. No dashboard card was added. `OIL`, `OIL BRENT` and `OIL WTI` are unchanged.
- **Local result (2026-11-14, real stored data):** 10 derived months, 2026-01 to 2026-10, and 12 Brent months (2025-01 to 2025-12) omitted for lack of FX. January 2026 is `partial_source_window` (5 FX days, 13 observations): Brent 66.8, FX 19.80499666..., 1,322.97 ZMW/bbl. October 2026 (latest): Brent 125, FX 19.9742 over 22 days and 66 observations, 2,496.775 ZMW/bbl. An independent PostgreSQL query (daily averages by Lusaka date, then their mean) matched the application result to PostgreSQL's available `avg` precision with identical day and observation counts, and an exact rational-arithmetic re-derivation from the stored rows matched all 10 months to better than 1e-35. The stored BoZ history is sparse in places: February 2026 rests on 1 FX day (2 observations) and March on 8 days, so the day and observation counts should be read with every value.
- **Licence:** `OIL ZM` inherits World Bank Brent as an input. While workbook applicability of the catalog licence is unconfirmed (see "Global oil benchmarks (monthly)"), it must not be described as freely redistributable; this does not block local development.
- **Future (not implemented):** comparing `OIL ZM` with ERB petrol/diesel (lagged comparisons or spreads) belongs to the later analytics work.

## Sovereign auction yield curve (derived)
- **What it is:** a ZM Terminal **derived** research view, `curve_type = published_auction_yield_tenor_curve`: for each published BoZ tenor (T-bills 91D, 182D, 273D, 364D; Government bonds 2Y, 3Y, 5Y, 7Y, 10Y, 15Y) the latest **stored accepted** auction yield at or before an as-of date. It is not an official BoZ curve and not a zero-coupon, spot, par, fitted (Nelson-Siegel/Svensson/spline), bootstrapped, constant-maturity or remaining-maturity curve. The component yields remain official BoZ auction observations.
- **Stored-only:** it reads `treasury_bill_auctions` and `government_bond_auctions` and nothing else (no BoZ call, no OpenBB, no writes). Nothing derived is persisted and there is no migration 010; the two source histories stay authoritative.
- **Snapshot (as-of) method:** each tenor is selected independently as the stored row with the greatest `auction_date <= as_of` (ties on one date go to the higher tender number). `as_of` is only the cutoff, never a common observation date. `latest` uses Africa/Lusaka today. `GET /api/v1/yield-curve/as-of?date=YYYY-MM-DD` takes a strict date (malformed or future dates are 422; no observation on or before it is 404; a database failure is a safe 503; there is no upstream 502/504 path).
- **Mixed auction vintages:** points normally come from different auction dates. The response states `mixed_vintage`, `oldest_point_date`, `newest_point_date` and `vintage_span_days`, and each point keeps its own `auction_date`, `tender_number`, `isin` and `age_days` (as_of minus auction_date, a plain calendar-day count; not a stale, liquidity or maturity measure). There is no whole-curve freshness claim.
- **Points:** `instrument_type` (`treasury_bill` or `government_bond`), the published `tenor`, `tenor_order` (a categorical display position, not a maturity), `yield_rate` in percent per annum exactly as published (`yield_unit = percent_per_annum_as_published`, never divided by 100, Decimal), `source = boz` and `source_url`. T-bill points add `discount_rate` and bond points add `coupon_rate` as supporting metadata only; the curve never uses them as the yield.
- **Published tenor buckets, not remaining maturities:** the stored bond rows hold the tenor bucket, ISIN, coupon and yield but **no maturity date**, and BoZ reopens existing bonds (the same ISIN and maturity auctioned again at a new yield: for example the 10Y ISIN `ZM1000007642` appears in 5 stored auctions with an unchanged coupon). So a bond tenor label is not an exact remaining maturity and no maturity date, remaining maturity, discount factor or spot/forward rate is derived or exposed.
- **No interpolation:** a tenor with no stored accepted observation on or before the date is omitted and listed in `missing_tenors`; no adjacent tenor is substituted and no value is created between tenors. A curve is returned if at least one point exists.
- **Accepted observations only:** the histories store accepted observations; rejected source tenders are not persisted and are not reconstructed. A point is therefore the latest stored accepted observation, not necessarily the latest BoZ auction (for example, rejected T-bill tender 23/2026 of 2026-11-12 is not stored, so the T-bill points come from tender 22/2026 of 2026-10-29).
- **UI:** `CURVE ZM` and `YIELD CURVE ZM` open `ZAMBIA SOVEREIGN · AUCTION YIELD CURVE` (no dashboard card): a `DERIVED` badge, the as-of date, the mixed-vintage status with oldest/newest auction dates and span, a categorical SVG chart (fixed tenor slots 91D..15Y, visible markers, T-bills and bonds distinguished, tooltips only on the markers; the dashed connector is visual only and is never drawn across a missing tenor), the missing-tenor list, the full point table (tenor, yield, instrument, auction date, age, tender, ISIN, supporting rate) and a short provenance/methodology block. An `AS OF` date input rebuilds the snapshot from the stored data and `LATEST` resets it; each `CURVE ZM` command returns to the latest snapshot. The frontend renders and rounds only; the backend owns selection, age, vintage metadata, classification and methodology.
- **Local result (2026-11-14, real stored data):** as of 2026-11-14, 10 of 10 tenors, mixed vintages, oldest 2026-02-13 (5Y) and newest 2026-10-29 (T-bills), a 258-day span. T-bills 91D 8.5000, 182D 9.1000, 273D 9.5000, 364D 10.0000 (tender 22/2026, age 16 days); bonds 2Y 12.0000, 3Y 12.5900, 7Y 13.7500, 10Y 14.5000, 15Y 15.4500 (tender 07/2026/BA of 2026-09-25, age 50 days) and 5Y 14.9800 (tender 02/2026/BA of 2026-02-13, age 274 days: the last stored 5Y auction). Historical as-of snapshots checked against an independent SQL window-function query for 7 dates all matched, including a single-vintage snapshot (2025-12-19, 5 bond tenors, T-bills and 2Y missing).
- **Licence:** all points are BoZ auction observations; BoZ redistribution and commercial-use terms remain unreviewed and the derived curve does not change that.
- **Published-tenor spreads (derived, four fixed definitions only):** `metric_type = published_tenor_yield_spread`. Each spread is `long_yield_rate - short_yield_rate` in basis points (`(long - short) * 100`, exact Decimal, computed in the backend, never in the UI) between two points of the curve snapshot above: `10Y_364D` (10Y - 364D), `15Y_364D`, `10Y_2Y` and `15Y_91D`. `app/services/yield_spreads.py` only does arithmetic on the already-derived `YieldCurve` (no second selection policy, no database access, no upstream call, nothing persisted, no migration 010). Routes: `GET /api/v1/yield-curve/spreads/latest` (Africa/Lusaka today) and `GET /api/v1/yield-curve/spreads/as-of?date=YYYY-MM-DD`, with the curve's date rules (422 malformed or future, 404 no curve, safe 503). The response lists `available_spreads` and `missing_spreads` (an endpoint tenor with no stored observation makes the spread unavailable; nothing is substituted, interpolated or zero-filled). Each spread carries both endpoint yields and auction dates, `same_vintage` and `vintage_gap_days`; because curve points usually come from different auction dates a spread is **not necessarily a same-date market spread**, and the notice says so. Negative and zero spreads are valid values and are not labelled: no inversion, steepness, flatness or regime interpretation exists.
- **Spreads UI:** the `PUBLISHED-TENOR SPREADS` section of the `CURVE ZM` view shows the four values (for example `+450 bp`, with `14.50% - 10.00%` and the two auction dates and gap), follows the same AS OF date as the curve (the UI requests spreads for the curve's own `as_of`) and shows `n/a` with the missing tenor when an endpoint is absent. Local result as of 2026-11-14: 10Y-364D +450 bp (10Y 2026-09-25 vs 364D 2026-10-29, mixed, 34 days), 15Y-364D +545 bp (15Y 2026-09-25 vs 364D 2026-10-29, mixed, 34 days), 10Y-2Y +250 bp (both 2026-09-25, same vintage), 15Y-91D +695 bp (15Y 2026-09-25 vs 91D 2026-10-29, mixed, 34 days).
- **Not implemented:** historical spread charts, spread time series, inversion/steepening/flattening interpretation, curvature, PCA, real-yield curves, term premium or any general curve-analytics engine; those are follow-ups.

## Bitcoin: BTC/USD (Bitstamp) and indicative BTC/ZMW (local/internal)
- **Status:** implemented for **local/internal use only**. Public display, API redistribution, commercial use and public derived BTC/ZMW remain `review_required` (Bitstamp's API page points commercial users to a Data License Agreement and its Terms of Use could not be read during research); the project owner chose to implement locally on that basis (`docs/research/btc-provider-discovery.md`, implementation decision update).
- **Source:** Bitstamp public API v2, market `btcusd` SPOT, no key. Direct adapter `app/services/bitstamp_btc.py` (OpenBB is not involved). Provider policy `bitstamp_btcusd_spot`: normalized storage allowed, raw storage disabled, redistribution and commercial use `review_required`.
- **Live BTC/USD:** `GET /api/v1/btc/usd/latest` returns the ticker `last` (the latest executed trade) with bid, ask and Bitstamp's rolling 24-hour high, low, VWAP and volume, the ticker timestamp, and a freshness flag (`BTC_STALE_AFTER_SECONDS = 300`, a ZM Terminal heuristic, not a Bitstamp SLA). One request, 10 s timeout, no retry, nothing stored (timeout 504, invalid or unavailable 502). **HTTP 200 is not trusted:** an unknown market path can return the all-markets array, so the adapter rejects arrays and requires an object with `last`, `timestamp`, `market_type == "SPOT"` and valid decimal strings; market identity rests on the `/ticker/btcusd/` path because the body carries no pair.
- **Daily history:** `btc_usd_daily` (migration `010_btc_usd_daily.sql`, apply manually to an existing database) holds completed UTC-day OHLCV candles, append-only with conflict detection (a differing stored candle fails the import; identical is a no-op). `python -m app.jobs.backfill_btc [--from] [--to] [--dry-run]` pages forward with `start` + `limit` (<= 1000, `exclude_current_candle=true`, about 1 s apart; never `end`, which overrides `start`), validates every candle strictly, and ends when the newest completed day is reached (Bitstamp can return fewer than `limit` candles while more exist, so a short page does not end the run). **Enforced by the importer:** ascending, non-duplicate timestamps, every page starting at or after the requested start without overlapping the previous page (so each non-empty page advances at least one day), a page limit, and failing closed on an empty page before the newest completed day. **Not enforced:** that every interior day exists; the importer does not prove daily continuity. **Edge:** shortly after UTC midnight Bitstamp may not yet expose yesterday's completed candle, in which case the import fails (nothing is written, stored rows are untouched) rather than declaring history complete, and it can be repeated later. Zero-volume candles are stored exactly as published (observed source behaviour; generation methodology not documented): never deleted, filled or inferred. `GET /api/v1/btc/usd/history?range=1M|3M|6M|1Y|3Y|5Y|ALL` is stored-only (503 on database failure) and never contacts Bitstamp. The ranges are rolling-day windows counted back from the request time, not calendar months or years: 1M = 30 days, 3M = 91, 6M = 182, 1Y = 365, 3Y = 1095, 5Y = 1825, ALL = unbounded (each cut-off is the UTC midnight of its first day). Daily `close` is the last trade of a UTC day, not an average.
- **Local import result (2026-11-14):** 5,567 candles, 2011-08-18 to 2026-11-13 (the newest completed UTC day), 33 zero-volume, 6 requests; a manual SQL check of this stored dataset found no gaps between consecutive stored days (an observation about this dataset, not something the importer guarantees); a repeat import inserted nothing (5,567 identical). Observed precision: prices up to 2 decimals and volume up to 8 (not a documented guarantee); stored as published.
- **Indicative BTC/ZMW (derived):** `GET /api/v1/btc/zmw/latest` = Bitstamp BTC/USD last x the latest complete **stored** BoZ USD/ZMW mid (`fx_store.fetch_latest_fx_mid`: newest complete USD/ZMW `boz` row), Decimal at 40 significant digits, no rounding, nothing persisted, **no BoZ request** (404 when no FX is stored, 503 on a database failure or an unusable stored observation (a non-positive or non-finite mid, or an observation in the future), 502/504 for Bitstamp, and a generic 500 for an unexpected derivation failure, which is never labelled as an FX problem). It reports both inputs with source, observation time and age, `btc_stale` (5 minutes), `fx_stale` (the unchanged BoZ rule, 96 hours via `boz.is_stale`) and `derived_stale` (their OR). Bitcoin trades continuously while BoZ publishes at business-day times, so an ordinary weekend shows a current BTC input and an older FX input that is still inside 96 hours; the UI shows both ages. It is not an exchange-traded BTC/ZMW price, a Zambian dealer, P2P or mobile-money quote, or an executable quote.
- **UI and commands:** `BTC` and `BTC USD` open `BITCOIN · BTC/USD` (`BITSTAMP SPOT`, rolling 24-hour values labelled as such, range controls and a close chart, latest completed candle and recent OHLCV table); `BTC ZMW` opens `BITCOIN · INDICATIVE BTC/ZMW` with the `DERIVED` badge and the `BTC/USD x USD/ZMW = BTC/ZMW` equation. Below the live equation it shows the `DERIVED DAILY HISTORY` section: range buttons, a line chart of real derived days only (the line joins them; missing dates are stated as omitted), a note that the inputs are not simultaneous, and a recent-days table with the BTC close, the BoZ daily mean, the observation count and the first-to-last observation times (CAT). Two market overview cards replace the old placeholders. There is no `BTC ZM` command (it could imply a Zambian Bitcoin market). The frontend does no arithmetic. The `BTC USD` view's REFRESH reloads only the live quote (one backend call, so at most one Bitstamp request); the stored history is read when the view opens and when its range changes, and never contacts Bitstamp. Opening the app triggers one BTC/USD and one BTC/ZMW backend call (the two market cards), and the development build's React StrictMode can repeat effects.
- **Historical derived BTC/ZMW (`btc_zmw_daily_v1`):** `GET /api/v1/btc/zmw/history?range=1M|3M|6M|1Y|3Y|5Y|ALL` (the BTC history rolling-day windows) derives each day on request from stored data only: `btc_zmw = btc_usd_daily_close x usd_zmw_daily_mid_avg`. `btc_usd_daily_close` is the stored completed Bitstamp UTC-day close (not an average, VWAP or live price). `usd_zmw_daily_mid_avg` is the arithmetic mean (equal weight, Decimal at 40 digits, no rounding) of all complete stored BoZ USD/ZMW mids (buy, mid and sell present, source boz) whose `observed_at`, converted to Africa/Lusaka, falls on the same calendar date as the candle's UTC date (the project's fixed UTC+2 `LUSAKA` zone; the rule is explicit and tested at the date boundary). A candle date with no eligible BoZ observation is omitted and counted in `btc_days_without_fx` (selected BTC dates of the requested range only; FX-only dates and dates outside the range are not counted): no forward-fill, backward-fill, interpolation, nearest-observation substitution, zero or null point. There is no weekday exclusion rule: in the current stored dataset this normally removes weekends and holidays because BoZ has no observation then, but a date derives whenever a matching eligible BoZ observation exists. Historical derivation validates all stored source rows loaded for the requested calculation window and fails the request (503) on invalid stored source data rather than silently skipping it, even if the row would not have produced a point. Each point carries the BTC close and candle time, the daily mean, the observation count and the first and last BoZ observation times. The two inputs are **not simultaneous**: the BTC daily close and the BoZ FX observations represent different observation times within the matched calendar date, so it is a derived analytical value, not a synchronized close, an official daily price or an executable quote. It is not persisted (no table, no migration 011), makes no upstream request (a test fails if Bitstamp or BoZ HTTP is reached; 503 on database failure or an invalid stored value; an empty range is a valid empty history). The response includes `fx_stored_from`, the first stored eligible BoZ date (global, not range-local): BTC/USD history begins in 2011 but the derived series can only start where the stored BoZ history overlaps it, so `ALL` currently shows the same window as `1Y`. Local result (2026-11-14): 167 derived days from 2026-01-22 to 2026-11-13, 5,400 of the 5,567 stored BTC days omitted for no BoZ observation, a match with an independent SQL computation on every day. The live quote is a different quantity (current Bitstamp last x the latest stored mid) and is never replaced by the latest historical point.
- **Not implemented:** BTC/ZMW persistence, tick storage, a scheduled import, a public deployment.

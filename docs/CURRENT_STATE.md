# Current state

Implemented and verified on branch `feat/usdzmw-vertical-slice`:

- **BoZ USD/ZMW adapter** (`GET /api/v1/fx/USDZMW`): unchanged validation and error behaviour (504 timeout, safe 502, 96 h stale flag, no OpenBB dependency).
- **Persistence**: successful quotes stored in `fx_rates` (exact decimals, `retrieved_at`, `source_url`); idempotent; no raw payloads. Persistence failure does not fail the quote request.
- **History**: `GET /api/v1/fx/USDZMW/history?range=1D|1W|1M|3M|1Y|ALL`.
- **Provider policy**: `app/services/provider_policy.py`, exposed at `GET /api/v1/providers` (three BoZ datasets: USD/ZMW rates, Treasury Bill and Government Bond auction results).
- **Historical backfill** (`python -m app.jobs.backfill_usdzmw`): bounded, atomic, idempotent import of BoZ observations from 2026-01-22 using the official JSON view's date filter; conflicts abort without overwriting; valid off-slot rows are reported as not selected. Manual only (no scheduler or HTTP endpoint).
- **Web**: live USD/ZMW card, USD/ZMW detail view with provenance, range selector and Lightweight Charts `mid` line; command palette with `FX USDZMW` and `USDZMW` only.
- **CI**: API job runs a PostgreSQL service so the integration tests execute.

Not implemented: history before 2026-01-22 (the JSON view has none; the XLSX archive was not ingested, see README), LuSE, T-bill history/PDF-only fields, BTC, copper, macro, watchlists (static placeholders), other commands, authentication, alerts, history backfill from BoZ, scheduled ingestion, frontend tests, a frontend lint step.

Known limitations:

- History is limited to what the JSON view serves (from 2026-01-22) plus quotes retrieved by this app. The filter's timezone is undocumented (harmless for whole-day windows given the 07:30-13:30 UTC slots).
- A few published rows are inconsistent and stored as published, e.g. buy > sell on 2026-03-19 07:30Z and 10:30Z; the live adapter and backfill share one source-selection policy (UTC hours 07/10/13, mirroring the BoZ site's latest-rate selection; its series chart is unfiltered, and unlike the site there is no fallback), so rows in those slots are trusted as published.
- A conflicting stored row is detected (safe warning) but not resolved: the live quote is returned unsaved and the stored row is kept; there is no reconciliation tool.
- T-bills: BoZ published tender 23/2026 (2026-11-12) with a duplicated 273-day record (the 182-day values filed under 273). It is rejected whole and reported in `skipped_tenders`; rows fall back to tender 22/2026.
- Redistribution and commercial-use terms of BoZ data are unreviewed.
- Migrations are plain SQL in `db/init` (applied automatically only on a fresh database volume).

## Treasury Bills (feat/boz-treasury-bills)
- Source: official BoZ Drupal JSON:API `/jsonapi/node/tbills_auction_results` (what the BoZ Treasury Bills page itself reads; public, no auth). One node per tender (`title` "22/2026", `field_tbills_auction_date`) with one included paragraph per tenor (91/182/273/364 days): ISIN, yield, discount. Field names differ per tenor and are matched strictly. Amounts, cut-off and yield ranges exist only in linked PDFs and are **not** modelled (no PDF parsing).
- `GET /api/v1/treasury-bills/latest` (newest row per tenor, each with its own auction date; `missing_tenors`, `skipped_tenders`) and `GET /api/v1/treasury-bills/{91D|182D|273D|364D}` (422 invalid tenor, 404 none recent, 504 timeout, 502 other). Fetches the 5 most recent tenders per request; a tender failing validation (bad number/date/ISIN/rate, duplicate tenor) is rejected whole, never repaired. `stale` = auction older than 21 days (heuristic).
- Persistence: `treasury_bill_auctions` (`db/init/003_treasury_bill_auctions.sql`, apply manually to existing volumes), unique on `(auction_date, tender_number, tenor_days)`; same conflict-aware rules as `fx_rates` (identical = no-op, different = rollback, never overwritten). Best-effort: the live response is returned if saving fails.
- No history endpoint yet (the API can page the archive; left for the next task). Commands: `TBILL ZM`, `TBILL 91D|182D|273D|364D`. No frontend test runner exists, so command parsing is verified by `tsc` only.

## Government Bonds (feat/boz-government-bonds)
- Source: official BoZ Drupal JSON:API `/jsonapi/node/bond_auction` (what the Government Bonds page reads; public, no auth). One node per auction (title `07/2026/BA`); `field_bond_auction_date` is an ISO datetime with explicit +02:00 offset, its calendar date being the auction date (every 2026 value is a Friday); one included `paragraph--<N>_year(s)_bond` per tenor (2/3/5/7/10/15) with ISIN, coupon, yield. Field names differ per tenor and are matched strictly; the tenor label must agree with the record type. Nodes before 12/2025 are empty placeholders (rejected as "no published tenors"). Amounts, cut-off coupon/yield and ranges exist only in PDFs and are **not** modelled.
- Reopenings: 7Y/10Y/15Y repeat the same ISIN and coupon across auctions with new yields; 2Y/3Y (and 5Y) are new ISINs. Identity is `auction_date + tender_number + tenor_years`, never the ISIN.
- `GET /api/v1/government-bonds/latest` and `/{2Y|3Y|5Y|7Y|10Y|15Y}`: newest row per tenor among auctions that contain it; `missing_tenors`; `skipped_tenders` (informational); per-row `newer_rejected_tenders` (rejected auctions dated after the row; non-empty = fallback; same semantics as T-bills). Discovery walks the BoZ archive newest-first, 50 auctions per page via the API's own `links.next` (same endpoint only), sequentially, stopping once all six tenors have a valid row or the archive ends (currently 3 requests: the archive is 110 tenders, 8 with data); a 10-page cap that is reached with tenors unfound and a `next` link still present fails closed (502). So `missing_tenors` means "not in the whole archive". A tenor can therefore come from an old auction (5Y: 02/2026); no stale flag. Duplicate auctions across pages collapse if identical and fail if conflicting. 422 invalid tenor, 404 none recent, 504 timeout, 502 other.
- **No `stale` flag** by design: the issuance calendar is a quarterly PDF (not machine-readable) and observed gaps between 2026 auctions were 21 to 63 days, so no defensible threshold exists. Each row shows its own auction date.
- Persistence: `government_bond_auctions` (`db/init/004_government_bond_auctions.sql`; apply to an existing volume with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/004_government_bond_auctions.sql`), unique on auction identity; same conflict-aware rules as T-bills; best-effort save.
- Live finding (2026-11-12): tender `03/2026/BA` has a malformed 15Y ISIN (`ZM100007709`, 11 characters). It is rejected whole and reported neutrally (older than every displayed row, so no fallback claim).
- Commands: `BOND ZM`, `BOND 2Y|3Y|5Y|7Y|10Y|15Y`; dashboard card `10Y GRZ BOND`. No history, no yield curve.
- **Validation granularity:** tender-level failures reject the whole tender (bad tender number or date, malformed/duplicate references, a referenced record missing, two records for one tenor); tenor-level failures (invalid ISIN/coupon/yield, label mismatch, unpublished record, unknown record type) reject only that record and valid siblings stay usable. Nothing is repaired or trimmed. Rejections are kept as `{tender_number, auction_date, affected_tenors, scope}` (no error text). A valid tender with zero result records is "no results", not a rejection. Valid tenors this adapter does not model (e.g. a 20-year record) are ignored.
- **Fallback rule:** a row is a fallback only if a rejected record dated strictly after it could have carried that same tenor (its own tenor, or a tender-level rejection). `unverified_tenors` lists missing tenors a rejected record could have carried.
- **Live (2026-11-12):** BoZ's archive has 110 tenders, 8 with data; each of 12/2025, 01/2026, 02/2026 and 03/2026 had one malformed ISIN in a different tenor (15Y, 7Y, 3Y, 2Y). Their other tenors are now accepted, so 5Y resolves to 02/2026/BA (2026-02-13), and all six tenors are found in a single 50-auction page.

## Fixed-income history (feat/fixed-income-history, stacked on feat/boz-government-bonds)
- Manual jobs (no scheduler): `python -m app.jobs.backfill_tbills --from YYYY-MM-DD [--to YYYY-MM-DD] [--dry-run]` and `python -m app.jobs.backfill_bonds ...`. Both use the live adapters' parsers (T-bills: whole-tender rejection; bonds: tender-level vs tenor-level rejection), the collections' standard date filter (`field_tbills_auction_date`, `field_bond_auction_date` with +02:00 bounds), 50 per page, `links.next` (same endpoint only), sequential, 1 s apart, no retries, at most 10 pages (a truncated search fails). Future dates and `--from > --to` are rejected; every page is validated before one atomic write through the existing conflict-aware stores; `--dry-run` never touches PostgreSQL. Output is counts only. Empty "no results" tenders are counted separately, not as rejected.
- History APIs read stored rows only (never BoZ): `GET /api/v1/treasury-bills/history?tenor=91D|182D|273D|364D&range=1M|3M|6M|1Y|ALL` (default 364D, 1Y) and `GET /api/v1/government-bonds/history?tenor=2Y..15Y&range=3M|6M|1Y|ALL` (default 10Y, 1Y). Ascending by auction date, decimal strings, one point per real auction (a reopened ISIN gives one point per auction), no interpolation or forward-fill. 422 for invalid tenor/range, safe 503 if the database fails. `range` is relative to today (Africa/Lusaka).
- Migration `db/init/005_fixed_income_history_indexes.sql` adds `(tenor, auction_date)` indexes only (apply to existing volumes with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/005_fixed_income_history_indexes.sql`). Note: `003`/`004` must be applied too; the local dev DB lacked `treasury_bill_auctions` until this task (live T-bill saves had been silently best-effort failing).
- UI: each T-bill/bond detail view has a tenor + range selector and a Lightweight Charts yield line with one marker per auction; empty, single-point, loading and database-unavailable states.
- Real import (2026-11-12, dev DB): T-bills archive 336 tenders (2014-01-09..2026-11-12, only 21 with data, 315 empty), 52 valid rows from 13 tenders (2026-02-05..2026-10-29), 8 rejected tenders (23/2026 duplicate 273D; 14, 13, 12, 10, 08, 07/2026 have trailing whitespace in the tender number; 04/2026 has a 182D ISIN with trailing whitespace), 52 inserted, re-run 52 already present. Bonds: 110 auctions (102 empty), 39 valid rows (2025-12-19..2026-09-25), 1 tender-level and 4 tenor-level rejections, 39 inserted earlier via live reads, re-run 39 already present.
- Source-quality caveat: the T-bill parser deliberately does not trim whitespace, so six 2026 tenders whose only defect is a padded tender number are excluded from T-bill history. Deciding whether to accept them is a policy choice.

## ERB Zambia fuel (feat/erb-fuel)
- Source: ERB's public WordPress media API (`/wp-json/wp/v2/media?search=PUMP AND WHOLESALE PRICES&mime_type=application/zip`) locates the official archive ZIP (`.../uploads/files/PUMP-AND-WHOLESALE-PRICES-2012-2026.zip`, about 30 KB, one XLSX). Sheets `Wholesale Prices` and `Retail Prices ` (note the trailing space; matched after stripping). Monthly rows (`Year`, `Month`, then Petrol, Diesel, Kerosene, Jet A-1, Low Sulphur Gas oil in K/L); the wholesale sheet also has HFO/LPG/Bitumen (`Kg/L`, ambiguous unit, ignored). Retail covers 2012-01..2026-10 (the archive was published 2026-10-08, so the November press-release prices are **not** in it; they exist only as PDFs, which are not parsed). Month granularity: `effective_date` is the first day of the pricing month.
- **Precision rule:** ERB archive prices are normalized to the official workbook's displayed two-decimal ZMW precision. Binary Excel floating-point representation is not treated as additional published precision. Cells formatted `0.00`/`#,##0.00` become `Decimal(f"{v:.2f}")` and must equal the stored value within 1e-9; a cell whose stored value carries precision the format hides (135 wholesale cells, e.g. 20.00448 shown as 20.00) is rejected and counted, never rounded. `General` cells display up to 15 significant digits and are normalized through that. Any other format, header, sheet or value type fails the parse. `-`, blank and missing cells are "not published" (NULL), never 0.
- **Duplicate months:** the workbook lists some months twice (mid-month changes, no day given). All non-missing observations of a month/product are recorded before any is rejected. Identical usable duplicates collapse; if usable duplicates differ, or any duplicate is rejected (hidden precision, junk/non-finite/non-positive value), the whole product-month is ambiguous and omitted (`ambiguous_duplicate_cells`), never resolved by row order. A `-`/blank cell next to a valid value is not a competing observation and the valid value is kept. A single rejected observation is counted (`hidden_precision_cells` / `invalid_value_cells`) but is not "ambiguous". Result is independent of worksheet row order.
- **Wholesale precision:** retail/public pump prices use the official displayed 2dp precision; some wholesale cells carry higher precision and are preserved only where the workbook presents it (`General` format), never rounded away behind a `0.00` format (those are rejected). Float noise within 1e-9 in a `0.00` cell still normalizes to the displayed 2dp value.
- Table `zambia_fuel_prices` (`db/init/006_zambia_fuel_prices.sql`; apply to an existing volume with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/006_zambia_fuel_prices.sql`), unique on `(effective_date, product, price_type, unit)`, same conflict-aware rules (identical numeric = no-op, different = conflict, atomic rollback). Products `PETROL, DIESEL, KEROSENE, JET_A1, LSGO`; `price_type` retail/wholesale; unit litre.
- Job: `python -m app.jobs.backfill_fuel --from YYYY-MM-DD [--to YYYY-MM-DD] [--dry-run]` (manual; archive downloaded into memory only; counts only; future dates and `--from > --to` rejected; dry-run never touches PostgreSQL). It needs `openpyxl` (in `requirements.txt`; rebuild the API image to run it in-container; the API runtime itself does not import it).
- API (stored data only, ERB is never called): `GET /api/v1/fuel/latest` (newest retail per product + `missing_products`), `GET /api/v1/fuel/{PETROL|DIESEL|KEROSENE|JET_A1|LSGO}` (422 invalid, 404 none), `GET /api/v1/fuel/history?product=&range=1Y|3Y|5Y|ALL&type=retail|wholesale` (ascending, no interpolation, 503 on database failure).
- UI: `PETROL ZM` card; `FUEL ZM|PETROL|DIESEL|KEROSENE|JET|LSGO` opens the fuel view (latest table, per-product monthly retail chart with range selector). A neutral note appears when the newest stored month is before the current month.
- Real import (2026-11-12, dev DB): 370 workbook records examined, 1389 valid rows (retail: PETROL/DIESEL/KEROSENE 173 each, LSGO 141, JET_A1 49; wholesale: PETROL 143, DIESEL 143, KEROSENE 146, JET_A1 145, LSGO 103), 211 not-published cells, 135 hidden-precision wholesale cells rejected, 52 ambiguous duplicate cells omitted; 1389 inserted, re-run 1389 already present, 0 conflicts.
- Not implemented: PDF build-ups, the current month beyond the archive, wholesale in the UI, Jet A-1 posted airfield prices.

## ERB latest month + build-ups (feat/erb-fuel-buildups)
- **Discovery:** ERB's media API (`/wp-json/wp/v2/media?search=pump&mime_type=application/pdf`, up to 5 pages) lists the monthly PDFs; each is classified by filename (never a hard-coded month) into `press` (`/PressStatements/CurrentFuelPumpPrices<Month><Year>.pdf`), `pump` (`...PUMP-PRICE-BUILD-UP`), `wholesale` (petrol/diesel/kerosene) and `jet` (Jet A-1) under `/files/FuelPumpPrices/`. Only `https://www.erb.org.zm` PDFs are fetched (content type and size checked). Two different files for one month/kind are ambiguous and excluded. Files without a month in the name (e.g. `CurrentFuelPumpPrices-1-1-1.pdf`) are ignored. ERB's media listing has no documents for August 2026.
- **Parsing:** text-layer PDFs only (pdfplumber; `pdfplumber` is a job-time dependency, imported lazily). Strict: product heading, units, month, every component label, `-` = NULL (stored as NULL, never 0), `(2,117.40)` = negative, `24,721.03` parsed straight from text to Decimal. Unknown or duplicated rows fail the document. Two rows both labelled `TOTAL (Excl VAT)` get distinct codes by position (`TOTAL_EXCL_VAT_BEFORE_OMC_MARGIN` / `..._AFTER_OMC_MARGIN`). Renamed rows (`Wholesale Price to OMC` / `to the OMCs`, `Price in Metric Tonnes`...) map to one code only where they are the same row; the printed label is always kept. US$-priced wholesale rows are separate codes from K/M3 rows.
- **Supported layouts (verified, September 2025 to November 2026):** pump build-ups 14/14 months; petrol/diesel/kerosene wholesale 13/14 (not December 2025); Jet A-1 12/14 (not February/March 2026); text press statements for December 2025, January, February, March, May, July and October 2026. Not supported (counted as `unsupported_documents`, no one-off parsers): press statements for September-November 2025 (different effective-date wording), the odd wholesale/Jet layouts above, and everything before September 2025. XLSX remains the long-run price history.
- **Scanned press statements:** the press statements for April, June, September and **November 2026** are image-only PDFs with no text layer. They are reported (`scanned_documents`), never OCR'd, so **November 2026 retail prices are not ingested** and `/fuel/latest` still returns October 2026. The November pump build-up is stored (its uniform pump price is ERB's own figure in ZMW/m3, shown as such). The retail price is never derived from the build-up.
- **Effective date:** a press statement says the prices take effect "at midnight on 30th September 2026" for the October 2026 prices. Retail rows keep the archive's identity, the first day of the pricing month (2026-10-01), so XLSX and PDF rows for a month collide and are compared: identical = no conflict, different = conflict (nothing written). The statement's midnight date must be the day before the pricing month or the document is rejected. Build-up rows use the same `effective_date` convention.
- **Reconciliation (checks only):** a press price must be within 0.01 ZMW/litre of the build-up's uniform pump price divided by 1000 (ERB prints K/litre to 2 decimals; the build-up is in ZMW/m3, e.g. 33,061.35 ZMW/m3 = 33.06135 ZMW/litre vs a printed 33.06). A larger gap skips that month and is counted as a reconciliation failure. Neither value is ever replaced by the other. All 28 real press prices in the supported months matched the existing XLSX rows and the build-ups.
- **Schema:** `zambia_fuel_build_up_items` (`db/init/007_zambia_fuel_build_up_items.sql`; apply with `docker compose exec -T postgres psql -U zm_terminal -d zm_terminal < db/init/007_zambia_fuel_build_up_items.sql`): one row per product + component with `component_code`, source `component_label`, `position` (ERB order), nullable `amount`, `currency`, published `unit` ('' when none printed), `note` (printed rates/prose such as wharfage text), unique on `(effective_date, build_up_type, product, component_code, unit)`; Jet A-1 is `build_up_type = wholesale`, `product = JET_A1`. Same conflict-aware rules (NULL equals NULL; a NULL vs a published value is a conflict; one transaction for retail prices and build-ups).
- **Job:** `python -m app.jobs.backfill_fuel_buildups --from YYYY-MM [--to YYYY-MM] [--dry-run]` (months up to the current Lusaka month, at most 24, sequential, 1 s apart, no retries, counts only, dry-run never touches PostgreSQL). Needs `pdfplumber` (in `requirements.txt`; rebuild the API image to run it in-container).
- **API / UI:** `GET /api/v1/fuel/build-up?product=&type=pump|wholesale&month=YYYY-MM` (stored only; month optional = newest; 422 invalid, 404 none, 503 database). The fuel detail view has `RETAIL HISTORY | PUMP BUILD-UP | WHOLESALE BUILD-UP` for the selected product; rows are shown in ERB's order with the published unit, without claiming they add up.
- **Real import (2026-11-12, dev DB), 2025-09..2026-11:** 15 months, 56 documents found, 4 missing (August 2026), 4 scanned, 6 unsupported, 0 reconciliation failures, 28 retail rows (all already present from the XLSX), 1854 build-up items inserted (re-run: 1854 already present).
